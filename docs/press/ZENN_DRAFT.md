## 本文ドラフト

### はじめに

2026年6月にゲームを作り始めて、8月にiOS版をApp Storeでリリースしました。個人開発です。

- コミット数: 2,235
- GDScript: 258ファイル / 約102,000行
- ユニットテスト: 276ファイル / 1,734テスト
- 収録ダンジョン28種、ジョブ6種

コードのほとんどはCursor（AIエージェント）が書いています。

ただ、最初に正直に書いておきます。**「AIが全部やってくれた」わけではありません。** 手作業は想像以上に多く、土日は長時間コーディングしていました。

この記事で書きたいのは「AIってすごい」という話ではなく、**AIに数ヶ月規模のプロジェクトを任せ続けるために、人間側が何を整備する必要があったか**です。1日で終わるスクリプトを書かせるのと、10万行のプロジェクトを2ヶ月維持するのは、まったく別の問題でした。

---

### 問題1: AIは仕様を勝手に決める

最初の2週間で一番困ったのがこれです。

「敵の攻撃力を調整して」と頼むと、ついでにドロップ率も変えてくる。「UIを直して」と言うと、関係ないバランス値に手が入る。1回ずつは小さいのですが、2ヶ月続けると**ゲームバランスが誰にも説明できない状態**になります。

#### やったこと: セッションの役割を2つに分けた

Cursorのセッションを、役割で分離しました。

| 種別 | できること |
|---|---|
| **HQセッション** | 設計判断、タスクの発行、レビュー、仕様の更新 |
| **Implセッション** | 発行されたタスクの実装のみ。仕様判断は禁止 |

これをプロジェクトルート（`AGENTS.md`）に書いて、全セッションに常時読ませています。Implセッションには「指定タスクのスコープ外を実装しない」「仕様が曖昧なら推測せず質問する」を明記しました。

効果は思ったより大きくて、Implセッションが「この点は仕様が不明確なので確認します」と止まるようになりました。**AIに勝手にやらせないためのコストは、後から辻褄を合わせるコストよりずっと安い**です。

---

### 問題2: AIは文脈をすぐ失う

新しいセッションを始めるたびに、AIはプロジェクトのことを何も知りません。かといって仕様を毎回貼り付けるのは現実的ではない（トークンも時間も溶ける）。

#### やったこと: 仕様をリポジトリに置いて、Decision IDで管理した

チャットではなくファイルを唯一の正（SSOT）にしました。

```
docs/specs/
├─ core/          # 運用ルール
├─ game/          # ゲーム仕様
├─ decisions/     # 承認済みの設計判断（現在150件）
└─ implementation/
    ├─ CODEMAP.md # 現行コードの実態
    └─ ...
```

重要なのは `decisions/` です。設計を変えるときは必ずDecisionとして番号を振って記録し、元の仕様を上書きします。「なぜこうなっているのか」が後から追える状態を保つのが目的です。

半年後の自分もAIも、この150件を読めば意思決定の履歴をたどれます。逆に言うと、**これを書かないとAI開発は数週間で破綻します。** チャットログは検索できないし、AIは前のセッションを覚えていないので。

あわせて、タスク種別ごとに「どのspecを読むか」のバンドルを定義しました。Cursor Skillsとして切り出してあり、全文を読み込まずに必要な範囲だけ渡せます。

---

### 問題3: AIは同じバグを何度も踏む

これが一番おもしろかった部分です。

Godot 4のGDScriptには、LLMが繰り返し間違えるポイントがあります。たとえば:

- `maxf()` は引数を2つしか取れない（`maxf(a, b, c)` と書いてパースエラー）
- Pythonの `for ... else` は書けない
- `.tscn` / `.tres` のコメントは `;` のみ。`##` を書くとパースが壊れて、しかも**エラーにならずに既定値のまま動く**
- `Control.accept_event()` はあるが `InputEvent.accept_event()` はない

厄介なのは、これらが**起動時に即死する**タイプのエラーで、しかもAIが学習データ由来の思い込みで何度でも同じ書き方に戻ってくることです。

#### やったこと: 踏んだ落とし穴を全部ルールにして常時注入した

`.cursor/rules/` に再発防止ルールを置き、起動即死系だけを `alwaysApply: true` にして全セッションに常時読ませています。

```
| 症状 | 再発防止 |
|---|---|
| 鍛冶屋入場で即終了 | maxf は最大2引数 → maxf(a, maxf(b, c)) |
| `.tres` で後続プロパティが無視される | コメントは `;` のみ。`##` 禁止 |
| ダンジョン入場で即終了 | 静的ヘルパ名を組み込みと被らせない（wrap→bb_wrap） |
```

現在15ファイル。運用ルールとして「バグを直したら、修正だけで終わらせずルールに追記する」を明文化しました。

ここで学んだのは、**ルールを増やしすぎるとトークンを食って逆効果**だということです。最初は全部を常時注入していたら、コンテキストが圧迫されて実装の質が落ちました。いまは2層に分けています。

| 層 | 内容 | 注入 |
|---|---|---|
| 起動・パース即死 | 短い表のみ | 常時 |
| 全カタログ | 詳細な既往一覧 | 必要時のみ |

### 問題4: AIの変更が壊していないか分からない

自動戦闘のゲームなので、バランス計算やドロップ判定のロジックが大量にあります。AIが1行変えたときに、それが3つ先のシステムを壊していないかを目視で確認するのは不可能です。

#### やったこと: ユニットテストを先に厚くした

GUT（Godot Unit Test）で276ファイル / 1,734テスト。実装より先にテストの土台を作りました。

AIにテストを書かせるのは相性がよくて、「この関数の仕様はこうです、テストを書いてください」と頼むと素直に書きます。むしろ**AI開発ではテストが唯一の客観的な検証手段**なので、ここをケチると後で全部やり直しになります。

Cursor Skillとして「テストを実行して結果を報告する」手順を定義してあり、実装セッションの終わりに必ず走らせています。

### アセット生成もエージェントに寄せた

コードだけでなく、ドット絵の生成もMCP経由で自動化しています。

- **PixelLab（MCP）** — キャラクター・敵・アイテムアイコンのドット絵生成
- **godot-agent-tools（MCP）** — Godotエディタの操作（シーン編集、スクリーンショット、テスト実行）

ここでも分担をルール化しました。ドット絵はPixelLab、背景や雰囲気のあるアートは自分で生成する、という切り分けです。**なんでもAIに投げるのではなく、AIが得意な範囲を定義して境界を引く**方がうまくいきました。

ちなみに、実機ビルドにMCPのアドオンが混入して**iPhoneで起動ロゴのまま固まる**という事故を1回やっています（これもルール化して再発防止済みです）。

### やってみて分かったこと

**AIエージェント開発は「AIに任せる」ではなく「AIが失敗しない環境を作る」作業**でした。

体感としての時間配分は、

- 仕様とルールの整備: 4割
- AIへの指示とレビュー: 4割
- 自分で書く: 2割

くらいです。コードを書く時間は確かに激減しましたが、**その分「何を作るか決める」「決めたことを文書として維持する」時間が増えました。** 設計と仕様管理の比重が上がるので、向き不向きはあると思います。

あと、AIは疲れないので**こちらが疲れます。** 2ヶ月で2,235コミットというのは、要するにレビューし続けたということです。
