## 大前提：誇張しない

GIGAZINE も電ファミも、AI 案件は読者の目が厳しい。「AI が全部作った」と書いた瞬間に信頼を失い、コメント欄で叩かれる。
開発者本人の言葉は **「AI も使いましたが、想像以上に手作業が多かった」** であり、これを隠さないこと。

**訴求すべきは「AI がすごい」ではなく「AI に長期プロジェクトを任せるための運用をどう作ったか」。**
2,235 コミット・102,000 行・1,734 テストという規模を、破綻させずに 2 か月でストアまで運んだ**仕組み**が記事の本体になる。

## 本文（GIGAZINE タレコミ / 各社メール共通）

```
[メディア名] 編集部 ご担当者様

はじめまして。個人でゲーム開発をしております、本田航希と申します。
記事のネタになるかもしれないと思い、情報提供させていただきます。

■ 何をしたか

AIエージェント（Cursor）に設計判断と実装の両方を任せる開発運用を自分で設計し、
その運用だけでスマートフォン向けRPG『Crownfall』を約2か月でApp Storeに
リリースしました。現在も更新を続けています。

規模は以下の通りです。

　開発期間：2026年6月18日〜（初コミット）
　コミット数：2,235
　GDScript：258ファイル／約102,000行
　ユニットテスト：276ファイル／1,734テスト
　設計判断の記録（Decision Log）：150件
　収録ダンジョン：28種、ジョブ6種

■ なぜ記事になりうると考えたか

「AIでコードを書かせた」という話は既にありふれています。
今回お伝えしたいのは、その先にある「AIに数か月規模のプロジェクトを
任せ続けるには何が必要だったか」という運用の話です。

具体的には、次のような仕組みを作りました。

1. 役割を2種類のセッションに分離した
　　設計判断を下す「HQセッション」と、決まったタスクだけを実装する
　　「Implセッション」を分け、実装側が仕様を勝手に決められないようにしました。
　　AIが暴走して仕様が発散する問題への対処です。

2. 仕様を単一の正（SSOT）としてリポジトリに置いた
　　AIは会話の文脈をすぐ失うため、仕様をチャットではなくファイルに置き、
　　設計変更は「Decision ID」単位で承認・記録する形にしました。現在150件。

3. 踏んだ失敗を「ルール」に変換して蓄積した
　　起動不能やパースエラーを踏むたびに、修正して終わりにせず、
　　再発防止ルールとしてカタログ化し、以後のAIセッションに自動注入しています。
　　「Godotのmaxf関数は引数2つまで」といった、AIが繰り返し間違える
　　プロジェクト固有の落とし穴が現在15ファイル分たまっています。

4. アセット生成もエージェント化した
　　ドット絵はPixelLab、エディタ操作はGodot向けのMCPサーバ経由で、
　　AIが直接生成・配置できるようにしています。

5. この運用一式をテンプレートとして切り出し、公開しています
　　（docs/templates/godot-solo-cursor-kit/）

■ 正直に書いておきたいこと

「AIが全部作った」わけではありません。手作業は想像以上に多く、
土日は長時間コーディングしていました。
むしろ強調したいのは、AIに任せられる範囲を広げるために、
人間側がどれだけルールと仕様を整備する必要があったか、という点です。
そこが、同じことをやろうとしている方の役に立つ部分だと思っています。

■ 作ったゲームについて

『Crownfall』は、プレイヤーが自分では戦わない自動探索ハクスラRPGです。
指揮官として編成・装備・行き先だけを決め、戦闘は観察します。
iOS向け、基本プレイ無料、日本語対応。広告SDK・解析SDKは使っていません。
```

## 送付順序（重要）

1. **先に Zenn 記事を公開する**（`ZENN_DRAFT.md`）
2. X とはてなブックマークで拡散を試みる
3. **反応が出てから**上記を GIGAZINE のタレコミ窓口へ送る

GIGAZINE は「すでに話題になっているもの」を拾う傾向が強い。技術記事なしで送るより、記事の URL を添えて送る方が確率が上がる。逆に電ファミ・gamebiz は開発論そのものを扱うので、記事の有無にかかわらず送ってよい。
